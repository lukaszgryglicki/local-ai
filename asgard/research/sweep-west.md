## Report: open-weight thinking/coding LLMs for the Quadro RTX 5000 (15.5 GiB usable, llama.cpp Vulkan) — verified 2026-09-11

**Method (all numbers fetched, none from memory).** Org listings via `https://huggingface.co/api/models?author=<org>&limit=200&sort=createdAt&direction=-1`; architecture from each repo's `resolve/main/config.json`; GGUF sizes from `https://huggingface.co/api/models/<repo>/tree/main?recursive=true` (multi-part summed, mmproj/MTP excluded); per-tensor quant types, `token_embd` sizes and k-quant fallbacks read directly from GGUF headers (HTTP range reads of the first 30–40 MB of the file, `.../resolve/main/<file>.gguf`); llama.cpp status from `src/llama-arch.cpp` and `ggml/src/ggml-vulkan/ggml-vulkan.cpp` on master + GitHub issues.
**Arithmetic.** KV(q8_0 @262,144) = n_full × 2 × n_kv × head_dim × 1.0625 B × 262,144. SWA cache = n_swa_layers × 2 × n_kv × hd × 1.0625 × (window + 512 n_ubatch). Mamba2 state = layers × (heads×head_dim×d_state×4 B + conv_dim×3×4 B). VRAM = (file − token_embd[−per_layer_token_embd]) + KV + SWA + state + 1.2 GiB. tg ≈ 1000 / (bytes_read_per_token/300 GB/s + 2 ms); for MoE bytes_read = non-expert + (top_k/n_exp)×expert bytes. T1(ii)/T2 use exactly the user's k-layer CPU/GPU formulas (30 GB/s, +0.2 ms/layer). Full calculator output is reproduced in the per-model blocks.
**Verified llama.cpp facts that drive the KV numbers:** Gemma 4 stores K and V even when K==V (`src/llama-kv-cache.cpp`, has_v = !is_mla); Gemma 4 global layers use head_dim 512, SWA layers 256 (`conversion/gemma.py` → `gemma4.attention.key_length=512 / key_length_swa=256`, confirmed in GGUF headers); KV-shared layers (E2B/E4B) allocate nothing; hybrid archs allocate KV only for attention layers (per-layer `head_count_kv` arrays are `0` for Mamba layers in the Nemotron GGUF headers). Vulkan flash-attention accepts any head size that is a multiple of 8 and Q8_0 KV (`ggml-vulkan.cpp` FLASH_ATTN_EXT supports_op, ~L19270-19316), so Gemma 4's 512-wide heads + q8 KV are OK. `-fa on` is mandatory at 262K.

### 3. llama.cpp / Vulkan-specific notes for the passing models

- **Vulkan SSM kernels (all Mamba2 hybrids: Nemotron-H/Nano v2/Nano-3/Cascade-2/Lightning, Falcon-H1R, Granite-H):** added in PR #16463 "vulkan: Add State Space Model (SSM) Operations Support" (2025-10-17), optimized in #16645 and #18630; current `supports_op` for `GGML_OP_SSM_SCAN` requires **Mamba-2 layout (`is_mamba2`), `d_state ∈ {128, 256}`, `head_dim % 16 == 0`, F32 inputs, subgroup ops** (https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-vulkan/ggml-vulkan.cpp ~L19700-19736). Nemotron (d_state 128, hd 64/80), Falcon-H1R (d_state 256, hd 128) pass. **Jamba-Reasoning-3B (Mamba-1, d_state 16) fails the check → its 26 scan ops fall back to CPU** every token (functional but slow; historic report of corruption at the CPU↔GPU boundary in #19957, closed 2026-02-28 for the GDN case).
- **Gemma 4:** Vulkan FA supports head 512 + Q8_0 KV (see above). Issues: #24664 (closed 2026-06-16) Vulkan hang on Radeon 780M iGPU with Gemma-4 12B + MTP drafter; #28188 (closed 2026-09-01) Gemma4 + MTP crash on Vulkan/Strix Halo; #27460 (open) draft-mtp crashes on Vulkan/RADV (same class as #24492 "Gemma 4 31B MTP crashes on Vulkan"); #24132 (open) `GGML_SCHED_MAX_SPLIT_INPUTS` assert with gemma-4-E4B Q4_0 (CUDA report; scheduler-level, may affect E-series with CPU per-layer embeddings); #28509 (closed) 26B-A4B chat template `supports_typed_content` misclassification; #27698 (open, ROCm not Vulkan) gemma4moe load failure. Recommendation: run Gemma 4 **without** the MTP drafter on Vulkan.
- **Nemotron nemotron_h_moe:** #27141 (open, Metal) `GGML_ASSERT(K >= 1)` in `ggml_ssm_scan` during context reservation (Omni variant); #27717 (open) `--n-cpu-moe` below a threshold crashes MTP draft load for Lightning-30B-A3B (CUDA report, loader-level) — relevant because T2 here requires `--n-cpu-moe`/`-ot` expert offload; #20570 (closed same day 2026-03-15) Nano-3 mamba-base assert on CPU/ROCm/Vulkan. Expert tensors are IQ4_NL/Q5_0/Q5_1/Q8_0 (fallback) — all in the Vulkan dequant/mmq type lists (`case GGML_TYPE_IQ4_NL` at ggml-vulkan.cpp L4175/L4345/L8016).
- **cohere2moe (North Mini Code):** #28626 (closed 2026-09-09) MTP draft context allocated KV for every layer (deepseek2/glm4moe/cohere2moe); no Vulkan-specific issue found for `cohere2moe` or "North-Mini-Code".
- **gpt-oss:** no open Vulkan issue found (searched "gpt-oss vulkan", "openai-moe vulkan", "sinks"); #15274 (closed 2025-08) Jinja failure on Vulkan build only. #26346 (open) 6-8 % MoE prompt-processing regression on RDNA4 Vulkan (AMD only).
- **afmoe / falcon-h1 / jamba / granite:** no Vulkan-specific issues found beyond the SSM-kernel constraint above; #22940 (closed 2026-05) prompt cache disabled for FULL-only memory backends (Mamba/Jamba/hybrid) — check server prompt-cache behaviour for hybrids.
- General: #28368 (open) cache_prompt reuse changes logprobs; #27638 (open, Intel ANV) FA scalar fallback O(N²) — not NVIDIA. No Turing/NVIDIA-Vulkan-specific reports surfaced for these archs; FreeBSD NVIDIA Vulkan not covered by any issue found.
